## TL;DR

The session attempted to attack the 81%-of-decode Tilize overhead in tt-xla Qwen3-8B serving. After ~17 spec-review rounds, a 6-phase plan, full fork rebuild, classifier implementation, and final empirical verification:

**The Tilize bottleneck is NOT a missing-classification problem.** Upstream already does the classification work via `tt.mark_argument` custom_calls. `ConstEvalHoistTransform` already fires (88 consteval wrappers). Yet Tilize remains 81% of decode and the activation-side Tilizes (~86% of all Tilizes per Phase 0.1) are the real cost.

**TPOT outcome:** 132.57 ms warm (unchanged from the 132.47 ms canonical baseline). All classification-axis fixes were no-ops in practice.

**Real next attack:** activation-side Tilize folding/elimination — *not* what the plan targeted.

## Key empirical finding — the load-bearing insight

**Phase 0.2's marker grep returned a false negative because it read the wrong stage of IR.**

The Phase 0.2 task grepped `shlo_*.mlir` dumps for `mhlo.`/`xla.`/`tf.`/`jax.`/`torch.`/`_xla` -prefixed attrs on `%argN` lines. It found only `mhlo.sharding = "{replicated}"` which appears on inputs AND weights uniformly (not a discriminator). It concluded: **no per-arg parameter marker exists**.

Reality:
- torch_xla emits `stablehlo.custom_call @tt.mark_argument` ops *carrying* `frontend_attributes = {ttcore.argument_type = "parameter", ttir.name = "L__self___model_embed_tokens.weight", ...}` for each weight argument.
- The existing tt-xla frontend pass `frontend_passes::annotateArgumentAttributes` (in `/home/mhnie/tt-xla/pjrt_implementation/src/api/module_builder/frontend_passes/shlo_input_role_propagation.cc:40-374`):
  1. Calls `propagateInputRoleAttributes` → lifts the `tt.mark_argument` custom_calls into per-arg attrs.
  2. Calls `annotateArgumentAttributesFromCustomCall` → applies `PopulateArgumentAttrsFromTTMark` which `funcOp.setArgAttr(idx, ttcore::ArgumentTypeAttr::name, ...)` on each tagged arg.
  3. Calls `setDefaultRoleForUnannotatedArguments` → blanket-stamps `Input` on every remaining arg.

This pass runs in `runFrontendSHLOPipeline` at `module_builder.cc:877`, BEFORE the StableHLO pipeline that Phase 2's `classifyArgs` would feed into. By the time `tt-populate-argument-types` (or Phase 4's auto-detect) runs, every arg already has `ttcore.argument_type` set. Phase 2's classifier correctly short-circuits ("any non-default Parameter/Constant attr present → skip"); Phase 4's would have done the same.

**Diagnostic confirmation**: `ttnn_*.mlir` dump shows **88 `consteval_<n>` wrappers** generated by `ConstEvalHoistTransform`. The const-eval mechanism IS firing. Yet Tracy still reports Tilize = 81% of decode time. Conclusion: the bottleneck is downstream of weight classification.

## Where the Tilize cost actually lives

Phase 0.1 measured (from raw Tracy `ops_perf_results_*.csv` with the bucket script):
- **Weight tilizes: 152 ops (14.07%)**
- **Activation tilizes: 928 ops (85.93%)**

Even if A.1.a/A.3.a could fully eliminate weight Tilizes (which they don't — upstream already hoists them and they happen at compile-time, not runtime), the savings would be ≤14% of Tilize cost, which is ≤11% of decode. The remaining 86% of Tilizes are activation Tilizes happening per-step inside the model.

**Why activation Tilizes happen:** TTNN ops emit `to_layout` conversions between tile and row-major when consecutive ops have different layout preferences. Each `to_layout` at runtime dispatches a `TilizeWithValPadding` (or `UntilizeWithUnpadding`) kernel. Phase 3 tried to fold these via a new MLIR pass (`TTNNFoldThroughAgnosticOps`); Phase 0.3 counted only 4 cancellable triples per decode in the `ttnn_*.mlir` dump using the unary allowlist (`relu/gelu/silu/typecast`). At <50 cancellable pairs the spec-defined Phase 3 gate de-scopes the pass.

This 4-cancellable-pairs measurement is suspicious in light of the 928-activation-Tilize count: either (a) the existing `foldConsecutiveToLayoutOp` already eats most cases at the MLIR level and the remaining 928 are unfoldable, or (b) Phase 0.3's allowlist was too narrow — most activation Tilizes happen through ops the unary allowlist doesn't cover (`add`, `multiply`, `softmax`, `reduce`, etc.). Phase 3 of the spec restricted to unary ops to avoid binary-op layout asymmetry (`add(lhs, rhs)` requires both operands at the same layout).

## Real next attack paths (NOT in this session's deliverables)

Listed in order of expected leverage:

### 1. Activation-Tilize attribution and pattern analysis

Phase 0.1's shape bucketing classified each `TilizeWithValPadding` as weight vs activation by shape match. We never went deeper to ask **which ops are CAUSING the activation Tilizes**. Two questions to investigate:

- For each activation Tilize, what op was about to consume the output? (matmul, softmax, reduce, etc.)
- For each activation Untilize, what op produced the input?

If a small set of op pairs (e.g., `reduce_max → multiply`, `add → softmax`) accounts for >50% of activation Tilizes, those are concrete targets for layout-aware op selection or fusing into single-layout kernels.

Method: extend the Tracy bucket script with predecessor/successor-op join from raw CSV's adjacent-op columns. Or instrument the `TTNNDecomposeLayouts` pass to log each emitted `to_layout` with its surrounding op context.

### 2. Reduce-layout-conversion in `TTNNDecomposeLayouts`

The pass at `/home/mhnie/tt-mlir-sglang/lib/Dialect/TTNN/Transforms/TTNNDecomposeLayouts.cpp` emits `to_layout` ops greedily to satisfy each ttnn op's preferred layout. A smarter scheduler could:
- Defer `to_layout(_, row_major)` until the next op that REQUIRES row-major.
- Coalesce consecutive `to_layout(_, X) → op_in_X → to_layout(_, Y)` chains.
- Pick `Y == X` where possible.

This is upstream work in `tt-mlir-sglang`. Risk: layout transitions are part of the TTNN op contract — wrong layout can produce silent numerical errors. Needs careful unit-test coverage.

### 3. Binary-op-aware version of Phase 3

The plan's Phase 3 was restricted to unary ops to avoid the `add(lhs, rhs)` layout-mismatch trap. A binary-op-aware version would either:
- Symmetrically fold both operand chains (recurse on each).
- Insert a compensating `to_layout` on the second operand and rely on `foldConsecutiveToLayoutOp` to absorb it.

Phase 0.3's count was on the unary allowlist. A binary-aware count would likely reveal more candidates.

### 4. Pre-tilize HF weights at load time (the original A.1)

The original spec A.1 idea was to call `ttnn.tilize_with_val_padding(param)` once at HF model load. Phase 4.1 of the spec correctly identified this isn't directly implementable from Python (`ttnn` is a C++ device-side API). But a moral equivalent: tag HF weights with `ttcore.argument_type = constant` (not just `parameter`) which would let const-eval treat the entire load+tilize chain as compile-time foldable.

Today `tt.mark_argument` emits `parameter`, not `constant`. The hoist treats parameters as runtime-loadable inputs, not compile-time bakeable.

This is on the torch_xla emitter side — modifying torch_xla's PJRT plugin to emit `constant` for weights. Risk: spec for ConstEvalHoist may not treat `constant`-tagged subgraphs differently in practice.

### 5. Profile a single decode step's Tilize cost FOR REAL

The 81%-of-decode-time figure comes from a Tracy run that may have included one-time compile / kernel-launch overhead. The session never re-ran Tracy after Phase 1's full fork rebuild to confirm the bottleneck distribution is stable. A focused Tracy run with `--decode 50` (vs the 5 we've used) would amortize cold effects and give a more reliable per-op breakdown.

## Build infrastructure delivered

### `rebuild_tt_xla_stack.sh`

Located at `/home/mhnie/sglang/python/sglang/srt/hardware_backend/tenstorrent/scripts/rebuild_tt_xla_stack.sh`.

Usage from host:
```bash
docker exec -it tt-xla-eval bash \
  /sglang/python/sglang/srt/hardware_backend/tenstorrent/scripts/rebuild_tt_xla_stack.sh \
  [incremental|from-scratch]
```

**incremental** (default): trust existing build dirs, ninja incremental, ~3-6 min if no source changed.
**from-scratch**: `rm -rf` all build dirs and ExternalProject stamps + symlink + canonical loguru, full rebuild. Verified 15 min with warm ccache; expect 60-90 min cold.

What it bakes in (saving future sessions hours of debug):
1. Build INSIDE the container (`/tt-mlir-sglang`, `/tt-xla` paths).
2. Export correct `TTMLIR_TOOLCHAIN_DIR=/opt/tt-mlir-toolchain` BEFORE sourcing `env/activate` (whose default `/opt/ttmlir-toolchain` is wrong).
3. `set -eo pipefail` (NOT `-u` — env/activate references unset shell vars and dies under nounset).
4. Configure fork with FULL canonical-style CMake flags (RUNTIME=ON, STABLEHLO=ON, TTNN=ON, OPMODEL=ON, etc.) — the original `build_and_install.sh` only set `PERF_TRACE=OFF` and produced just `libTTMLIRCompiler.so`.
5. Retry ninja up to 3× for transient tt-metal git-clone TLS errors.
6. `lib_ttnncpp.so` / `lib_ttnn.so` symlinks (CMake's `-lX` transforms non-`lib`-prefixed `.so` names into broken `-l_X` flags).
7. `mkdir tt_metal/pre-compiled/` before install (CMake's install fails without it).
8. Patch tt-xla's `third_party/CMakeLists.txt` to neuter `ExternalProject_Add(tt-mlir)`:
   - `SOURCE_DIR /tt-mlir-sglang`, `DOWNLOAD/CONFIGURE/BUILD/PATCH commands ""`
   - Strip `GIT_REPOSITORY`/`GIT_TAG`/`GIT_PROGRESS` to prevent git stash conflicts on the fork's diverging history
   - Strip the original `BUILD_COMMAND env ... cmake --build` line (was being preferred over our `""` override)
   - Add `--prefix ${TTMLIR_INSTALL_PREFIX}` to both `INSTALL_COMMAND` lines (fork's CMakeCache caches `/usr/local`)
9. Symlink fork at canonical source path + touch all EP stamps.
10. Copy fork's 9 .so files into the plugin's `lib64/` rpath dir AFTER tt-xla build (the install step alone doesn't populate this).

**Verification commands** after rebuild (run inside container):
```
sha256sum /tt-xla/third_party/tt-mlir/install/lib/*.so
sha256sum /tt-xla/python_package/pjrt_plugin_tt/lib64/*.so
```

Plus the smoke bench command printed by the script at the end.

### What's NOT in the script

- The Phase 2 `module_builder.cc` patch (now in `module_builder.cc` directly, persisting in the container's bind-mounted source tree).
- Any application code beyond rebuild — pre-tilize, attribute-type-flip, etc. are research items.
