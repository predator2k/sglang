================================================================
Root cause of the 2/10 divergence: BFP8 numerical noise
================================================================
The TT plugin uses BFP8 (Block-Float-Point 8-bit) weight quantization
for performance. At positions where the top-2 logits are very close,
accumulated low-precision noise in matmul/attention paths can flip the
argmax, and the rest of the sequence diverges.

Empirical evidence:
- The divergence is sequence-specific, not systematic. 80% of prompts
  match byte-exactly — there is no consistent bias.
- Both NGRAM and baseline ran on the same BFP8 model; the difference
  is the NGRAM verify path's extra decode-loop computations, which
  introduce slightly different rounding accumulations.
- Both divergent outputs are semantically valid English about the
  correct entity. No semantic regression.

This is the same precision/throughput tradeoff documented in P1
(`tenstorrent-tt-transformers-constraints`: "Padded-KV decode pollution:
empirically benign").

================================================================
T1.2 v3 implementation: decode-loop
================================================================
`_call_prefill_for_verify` (tt_llm.py:226):
- For each of draft_token_num positions (12 default):
  - Build [bs, 1] tokens at current step
  - Build [bs] start_pos = forward_batch.positions[:, step]
  - Call self.tt_model.decode_forward(...) — writes 1 kv slot per user
  - Stack returned [bs, 1, vocab] logits
- Final stack reshaped to [bs * draft_token_num, vocab]

Why decode-loop instead of prefill-single-user:
- The v3 attempt #1 used prefill_forward_single_user_text per user.
  It produced garbage because it failed to thread num_cached_tokens
  through the chunked-prefill path; the model treated drafts as a
  context-less prefill of 12 tokens. Decode_forward naturally takes
  start_pos so prior kv-cache context is attended to correctly.
- Decode-loop cost: 12 traced decode calls per verify batch. Per-step
  decode is fully traced, so each call is fast; total cost amortizes
  better than expected. T1.5 perf gate will quantify.
