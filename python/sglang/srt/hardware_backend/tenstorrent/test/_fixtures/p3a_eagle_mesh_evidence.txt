Layout B — two separate (1,1) MeshDevices
================================================================
Attempted: 2026-05-13 21:37:00 (implicit via second TenstorrentQwenForCausalLM)
Result: **FAIL**
  - First model opened (1,2) mesh successfully (130s)
  - Second model called ttnn.open_mesh_device(mesh_shape=(1,2)) again
    via BaseMetalDeviceRunner._mesh_device(), which threw:
      TT_THROW: Device 0: Timed out while waiting for active ethernet
      core 30-25 to become active again.
  - Stack trace: ttnn::distributed::open_mesh_device →
                 MeshDevice::create →
                 MeshDeviceImpl::create
  - Root cause: BaseMetalDeviceRunner._initialize_mesh_device() does
    not accept device_ids; tt-metal MeshDevice cannot be opened
    twice in the same process even on disjoint device sets.
  - Recovery required: `sudo modprobe -r tenstorrent && sudo modprobe tenstorrent`
    plus `tt-smi -r 0,1` after each crash — the failed mesh init
    wedges the ETH link state on device 0.

Layout B is INFEASIBLE under the current tt-metal MeshDevice lifecycle.

================================================================
DECISION
================================================================
**Layout A (shared single (1,2) mesh) chosen for P3a.2 EAGLE work.**

Architectural impact for P3a.2 (EAGLE):
1. `BaseMetalDeviceRunner` needs an optional `external_mesh_device`
   constructor parameter (small refactor, ~10 LoC).
2. `TenstorrentQwenForCausalLM.__init__` needs to accept and thread
   through that parameter.
3. EAGLE worker setup will:
   - Build main model first → claims the shared (1,2) MeshDevice
   - Build draft model second → reuses main.mesh_device
4. Verify + draft kernels execute SEQUENTIALLY on the same mesh
   (this matches EAGLE's natural data flow — no concurrency needed).

Throughput risk: shared mesh means draft kernels share fabric with
main. Empirical delta to be measured in P3a.2 T2.4 (perf gate).
