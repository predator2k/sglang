IMPLICATIONS FOR PHASE B/D (HEAD UP, NOT A 0.5 BLOCKER)
-------------------------------------------------------
*** SPEC §10 RISK #5 IS REAL — this is the torch-pin risk the spec called out. ***

The sglang main branch hard-pins `torch==2.11.0` because of CUDA caching
allocator symbols introduced in 2.10/2.11. The tt-metal docker image bundles
torch 2.7.1+cpu and CANNOT trivially upgrade torch (tt-metal itself ABI-binds
against this exact wheel). Therefore Phase B MUST:

  (a) Gate quantization / pynccl / deep_gemm imports behind a CUDA-availability
      check or behind `SGLANG_PLATFORM=tenstorrent`, so that on the
      Tenstorrent build path we never reach `torch.cuda.memory._cuda_beginAllocate*`.
  (b) Avoid importing `model_runner` directly from any top-level Tenstorrent
      entry point; build a new tt-metal-specific runner that does not pull in
      the deep_gemm / pynccl chain.
  (c) For any CUDA-only model code, ensure the Tenstorrent dispatcher (Phase F)
      short-circuits before the offending modules are touched.

The good news: top-level `import sglang` and `from sglang.srt.server_args import
ServerArgs` BOTH work fine on torch 2.7.1+cpu, so the public CLI surface
(`launch_server.py`, ServerArgs parsing, request schemas) is already importable
without code changes. The CUDA-tainted modules are deeper in the runner stack.
